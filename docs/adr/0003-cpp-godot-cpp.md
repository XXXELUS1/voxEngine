# ADR-0003: C++ через godot-cpp 10 (не Rust, не C#)

- Статус: принято
- Дата: 2026-10-16

## Контекст

Диздок допускает «массивы и меши — C# или C++ (GDExtension)». Операции над 100 000+ вокселей и greedy
meshing в GDScript слишком медленны (десятки миллисекунд на кадр). Варианты нативного слоя:

- **C# (.NET)**: требует .NET-сборку Godot, усложняет экспорт (особенно консоли/мобильные), медленный
  интероп с движком на массивах, сборщик мусора в горячем пути.
- **Rust (gdext)**: отличная библиотека, но неканоническая: отстаёт от версий Godot, свой тулчейн,
  меньше примеров — агент чаще будет упираться в несовместимости.
- **C++ (godot-cpp)**: канонический путь GDExtension, тот же стиль, что у самого Godot, примеры на
  каждый класс, собирается `scons` на Linux/Windows/macOS, CI отдаёт готовые библиотеки.

Аргумент «язык должен быть понятен владельцу» не работает: владелец код не правит, а Claude одинаково
свободно пишет на любом из трёх.

## Решение

**C++17 через godot-cpp `10.0.0-stable`** (сабмодуль `src/voxbody/godot-cpp`, `api_version "4.7"`),
сборка `scons` (`scripts/build_ext.sh`, `make ext` / `make ext-release`), библиотека в
`godot/addons/voxbody/bin/libvoxbody.<platform>.<target>.<arch>.<ext>`. Для владельца на Windows
библиотеки собирает CI (артефакт `voxbody-windows`, MSVC). Стиль кода — как в Godot (табы, `snake_case`,
без исключений и RTTI). Граница: в C++ только то, что требует скорости или детерминизма; поведение
инструментов, реакции, UI — GDScript.

## Последствия

- Первая сборка ~10 минут (godot-cpp), дальше инкрементально; хук сессии запускает её в фоне.
- Обновление godot-cpp = обновление сабмодуля + `api_version` + прогон обеих целей и тестов.
- Каждое изменение API расширения отражается в `docs/spec/voxbody-api.md` и в headless-тестах
  `godot/tests/voxbody_tests.gd` — GDScript узнаёт о классах только через ClassDB.
- `reloadable = true` в `.gdextension`: редактор подхватывает пересобранную библиотеку, но при странном
  поведении редактор перезапускают.
