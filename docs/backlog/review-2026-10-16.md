# Бэклог ревью базы (16.10.2026)

Ревью остановлено до фазы исправлений ради экономии токенов (фокус сменился на визуал).
Находки ниже подтверждены скептиком-верификатором там, где указано `real`; остальные — без перепроверки.
Чинить, когда вернёмся к движку (C++) и перед выпуском генератора.

## cpp

- **cpp-1** [high, real] `src/voxbody/src/voxel_volume.cpp:113` — VoxelVolume::create() computes n = nx*ny*nz in int with no cap and no overflow check; when the product overflows, the three PackedByteArrays end up empty (or resize() fails on a negative size) while nx/ny/nz keep the requested dims, so in_bounds() says yes and every accessor (get_material, set_voxel, get_solid_min, count via idx()) reads/writes past the buffer. get_voxel_count() (voxel_volume.h:103) has the same overflow and can return a negative number. The same path is reachable from the storage property set_dims (a crafted .tres/.tscn) and from the .vxm loader (see cpp-2).
  - fix: Validate in create(): compute the product in int64_t, ERR_FAIL_COND_MSG when any dim is negative, when the product exceeds a sane cap (e.g. 1<<26 voxels, far above the 48^3 heads) or when material.size() != n after resize, and leave the volume at 0x0x0 on failure. Make get_voxel_count()/idx() use int64_t or rely on the cap so int math cannot overflow; set_dims() should go through the same validation.
- **cpp-2** [medium, real] `src/voxbody/src/voxel_model.cpp:221` — The .vxm loader computes nvox = (int64_t)dims.x * dims.y * dims.z and checks only `nvox > 1<<30`; with dims around 2^21 the int64 product overflows to a negative value, the cap is bypassed, the truncation check `offset + nvox > size` also passes (negative), slice() returns an empty array that set_material_data() accepts because create() produced an overflowed voxel count of 0, and load_from_buffer returns true with a part whose dims are 2^21^3 and whose fields are empty. Any later access crashes, and a VoxelModelNode pointing at such a file would crash in the mesher's padded-grid allocation on the first _process.
  - fix: Reject each dim individually before multiplying (e.g. 0 <= dim <= 4096 or dim <= 1<<15), then compute nvox in int64_t and compare against a cap well below 1<<30; also assert that vol->get_voxel_count() == nvox after create() and that the slice returned nvox bytes. Together with the create() validation from cpp-1 this closes the loader path.
- **cpp-3** [medium, real] `src/voxbody/src/voxel_volume.cpp:229` — carve_capsule and trim_hair_capsule decide voxel membership with float arithmetic (dot/len2 division, q = a + ab*t, squared distance) that is subject to FMA contraction. GCC defaults to -ffp-contract=fast and Clang to -ffp-contract=on, and the SConstruct / godot-cpp flags never pass -ffp-contract=off, so the arm64 builds the .gdextension declares (linux arm64, macOS universal) fuse a*b+c while the x86-64 baseline build (-march=x86-64, no FMA) does not. The header (voxel_volume.h:13-15) and ADR-0005 promise bit-identical results on every machine and specifically claim FMA cannot change the comparison for 1/16-quantised inputs; that claim is false, so networked clients on Apple Silicon vs PC would diverge on boundary voxels.
  - fix: Either add `-ffp-contract=off` (GCC/Clang) and `/fp:precise` without `/fp:contract` (MSVC) to CCFLAGS in src/voxbody/SConstruct for the voxbody objects, or (better, and in the spirit of ADR-0005) evaluate the capsule distance in exact fixed-point integers: quantise a, b, r to 1/16 voxel on entry and compute |p-a|^2*len2 - dot^2 <= r2*len2 in int64, which needs no division and is exactly deterministic. Update ADR-0005's claim accordingly and add a cross-build test vector (the input above) to voxbody_tests.gd.
- **cpp-4** [medium, real] `src/voxbody/src/voxel_model.cpp:232` — load_from_buffer allocates and zero-fills all three fields via vol->create(dims, ...) before it checks that the buffer actually holds nvox bytes for the part (the truncation check is at line 243, inside the fields loop). A tiny corrupt or truncated file with large dims therefore costs up to 3 GiB and tens of seconds before being rejected, which on a machine with less memory means an OOM kill of the game instead of an error.
  - fix: Before create(): count the known/unknown fields, verify offset + nvox * fields.size() <= size (and nvox <= cap) and only then allocate; alternatively build the volume directly from the slices. Lower the per-part cap from 1<<30 to something like 1<<26 so a malformed header can never request gigabytes.
- **cpp-5** [low, real] `src/voxbody/src/voxel_volume.cpp:273` — All bounding boxes in carve_capsule, stamp_state_sphere, bruise_sphere, burn_sphere and trim_hair_capsule cast floor()/ceil() of unclamped float expressions to int. For |value| >= 2^31 or INF/NaN the conversion is undefined behaviour; on x86-64 it yields INT_MIN, so x1 = min(nx-1, INT_MIN) is negative and the loop body never runs: the operation silently affects nothing although the geometry covers the whole volume. On AArch64 the same cast saturates to INT_MAX, so the identical call affects every voxel there, another platform divergence against the determinism contract.
  - fix: Reject non-finite inputs up front (ERR_FAIL_COND_V(!std::isfinite(...), 0)) and clamp the float box to [-1, n] before casting (e.g. `int lo(float f, int n) { return (int)std::clamp(std::floor(f), -1.0f, (float)n); }`), so huge radii degrade to 'whole volume' identically on every platform; a shared helper used by all five ops keeps them consistent.
- **cpp-6** [low, real] `src/voxbody/src/voxel_volume.cpp:537` — raycast() records the entry axis only when `t0 > tmin` with tmin starting at 0, so a ray whose origin lies exactly on the volume's entry face (t0 == 0) never sets entry_axis and reports a hit with normal (0,0,0) and distance 0, contradicting the header's promise that (0,0,0) only happens when the ray starts inside a solid voxel. Callers that re-cast from a previous hit position (surface position returned by raycast/raycast_local) get a zero normal, which tools.gd-style code then uses as the push-in direction.
  - fix: Use `t0 >= tmin` for the box clip (an origin on the boundary plane then records that axis; interior origins still have negative t0 and keep the inside semantics), and document that an origin on an interior solid face also yields a zero normal, or treat it the same way by checking whether the voxel behind the start point is air.
- **cpp-7** [low, real] `src/voxbody/src/voxel_volume.cpp:515` — raycast() validates max_dist and the direction length but not finiteness of the origin; a NaN origin passes the slab test (all comparisons false), the UB (int)floor(NaN) cast clamps to voxel 0 and the function returns hit=true for voxel (0,y,z) with position containing NaN, which then propagates NaN into cut()/bruise() through VoxelPart.
  - fix: Return the miss dictionary when any component of origin or dir is not finite (std::isfinite), before the slab clipping.
- **cpp-8** [low, real] `src/voxbody/src/voxel_model.cpp:208` — load_from_buffer mutates the model in place (model_name, voxel_size, palette, materials, meta and parts.clear()) before all validation is done, so a failed load leaves the receiving VoxelModel wiped or half-populated instead of untouched. This matters for the planned snapshot path (ADR-0005 §3: save_to_buffer/load_from_buffer on join), where a corrupt snapshot would destroy the client's current model.
  - fix: Parse into locals (name, size, palette, materials, meta, TypedArray parts) and commit them to the members only after the last ERR_FAIL check succeeds.
- **cpp-9** [low, real] `src/voxbody/src/voxel_model_node.cpp:38` — set_model_path() stores the new path before calling load_model(); when the load fails the node keeps the old model and old part children but reports the unloadable path, so model_path, model and the children disagree (e.g. VoxelLab.reload_model() reads head.model_path and would keep retrying the bad file while showing the old head).
  - fix: In set_model_path, only assign model_path after load_model() succeeded (or clear model/children on failure so the three stay consistent), and make load_model() the single place that writes model_path.
- **cpp-10** [low, real] `src/voxbody/src/voxel_model.cpp:175` — Palette entries from the header are divided by 255 without clamping, so values outside 0..255 (or non-numeric entries that convert to 0) produce Color components far outside [0,1]; the mesher writes them straight into ARRAY_COLOR and save_to_buffer later clamps, so a round trip silently changes the palette.
  - fix: Clamp each channel to 0..255 (or ERR_FAIL on out-of-range values, matching the spec's 'до 256 цветов [r,g,b] 0..255') and skip entries whose components are not numbers.
- **cpp-11** [low, real] `src/voxbody/src/voxel_part.cpp:340` — raycast_global() calls get_global_transform() unconditionally; on a VoxelPart that is not inside the tree the engine prints 'Condition !is_inside_tree() is true' on every call and the ray is cast against an identity transform, giving a plausible-looking but wrong hit instead of a clean miss.
  - fix: Return the miss dictionary (optionally with a push_warning) when !is_inside_tree(), or fall back to get_transform() explicitly and document it.
- **cpp-12** [low, real] `src/voxbody/src/voxel_volume.cpp:527` — For an axis with zero direction the slab test accepts o[i] == bmax[i] as inside (`o[i] > bmax[i]` is false), and floor(bmax) is then clamped to n-1, so a ray that slides exactly along the far boundary plane (e.g. y == ny) is treated as travelling through the last voxel row and reports hits on voxels it only grazes; the near plane (o[i] == 0) is accepted symmetrically but there floor() gives row 0, so the two boundaries behave differently.
  - fix: Use the half-open convention consistently: treat o[i] >= bmax[i] as outside for zero-direction axes (and compute the start voxel with the same rule), or document that grazing rays count as hits.
- **cpp-13** [low, real] `src/voxbody/src/voxel_volume.cpp:112` — create() accepts voxel_size <= 0 (and NaN) without complaint even though the loader rejects it; VoxelPart then silently substitutes 1.0 in get_vs() for conversions while the mesher still multiplies by the stored 0, so the part's mesh collapses to a point at origin and local_to_voxel/voxel_to_local disagree with the geometry.
  - fix: ERR_FAIL_COND_MSG(!(p_voxel_size > 0) || !std::isfinite(p_voxel_size)) in create()/set_voxel_size and drop the 1.0 fallback in VoxelPart::get_vs so the inconsistency cannot arise.

## voxgen

- **voxgen-1** [medium, real] `tools/voxgen/voxgen/io_vox.py:311` — import_vox silently turns every voxel painted with a colour slot that is not in the side-car `slots` table into air (material 0), so any new colour the owner picks in MagicaVoxel deletes those voxels on re-import with no warning.
  - fix: In `to_model`, after building `lut_c/lut_m`, find slots present in the XYZI that are not in `slot_map`; map them to `palette.nearest(vox['palette'][slot-1][:3])` (adding the RGB to the palette if far) with a sensible material (MAT_GENERIC, or the material of the nearest known slot), count them, and surface the count as a warning from `import_vox`/`cmd_import_vox`. - **voxgen-2** [low, real] `tools/voxgen/voxgen/checks.py:184` — check_layer_order's hair rule ('hair must be 6-adjacent to skin OR hair') accepts any hair column of length >= 2 that is rooted on cartilage, bone, fat or muscle, because each hair voxel vouches for the other; the spec requires hair only outside skin.
  - fix: Replace the one-step adjacency test with a flood from skin through hair (what `body.hair_height` does with `base = skin` instead of `base = all non-hair solids`): `loose = hair & (height < 0)`. - **voxgen-3** [low, real] `tools/voxgen/voxgen/checks.py:136` — _mirror_index_x only handles an x=0 plane lying on a voxel boundary; when the plane passes through voxel centres (origin.x/voxel_size is a half-integer) and the part is not x-centred in its grid, it returns None and check_symmetry_x silently mirrors about the grid centre instead, reporting a perfectly symmetric part as ~100% asymmetric (error, exit 1).
  - fix: Compute `k2 = round(2*c)`; if `abs(2*c - k2) > 2e-3` bail out, else `xm = k2 - 1 - np.arange(part.nx)` (gives 2k-1-x for a boundary plane and 2k-x for a centre plane). Verified this map against `coords()` for nx 9/10/11/12 with boundary and centre planes.
- **voxgen-4** [medium, real] `tools/voxgen/voxgen/io_vxm.py:34` — The .vxm header never records `symmetric`, `budget` or `allow_exposed_bone`, so `voxgen check <file.vxm>` (and `preview`/`info` on a file) runs on a model where every part has symmetric=False and budget=None: the symmetry check is silently skipped and the budget check uses a different limit than `build` used.
  - fix: Write `symmetric`, `budget` and `allow_exposed_bone` into each part dict in `header_dict` (the C++ loader reads keys by name and ignores extras; add them as optional fields to docs/spec/vxm-format.md) and restore them in `from_bytes`. - **voxgen-5** [low, real] `tools/voxgen/voxgen/io_vox.py:301` — to_model ignores the nTRN `_t` translation that read() already parses: with a side-car, parts the owner moved in MagicaVoxel snap back to the old origin; without a side-car, every part gets a centred/floor origin so the relative placement of a multi-part model is lost.

- **voxgen-9** [low, real] `tools/voxgen/voxgen/body.py:91` — _layer_color auto-creates any unknown colour *name* with the material's default colour, so a mistyped palette name in a spec silently paints the layer with the default (usually the plain 'skin' index) instead of failing; after that even tint_region accepts the typo because the name was added to the palette.

- **godot-1** [high, real] `godot/scripts/tools.gd:229` — The razor pushes both capsule endpoints inward by a speed-dependent depth (0.5..4 voxels) while the capsule radius is only 1.2 voxels, so at ordinary stroke speeds (>~850 px/s) the whole capsule lies under the skin: voxels are removed and the HUD reports an op, but the surface layer stays intact and nothing visible happens (a hidden subcutaneous tunnel).
  - fix: Keep the capsule axis within reach of the surface: clamp depth to at most razor_radius_vox - 0.5 voxels (or make razor_max_depth_vox <= razor_radius_vox), or carve the full wedge per frame (capsule from the surface points to the pushed-in points, e.g. cut(a_surface, b_surface) plus cut(a_deep, b_deep) or a larger radius that grows with depth). - **extra** [medium, unverified] `:0` — src/voxbody/src/voxel_mesher.cpp:147 and :165 — the mesher's padded-grid index arithmetic is plain int, so a part that passes the loader's current cap (voxel_model.cpp:222, nvox <= 1<<30) can still overflow it: dims (32768,32768,1) is exactly 2^30 voxels and is accepted; pstride[2] = 32770*32770 = 1,073,872,900 fits, but base_p for d=2, k=1 at :165 = 1 + 32770 + 1,073,872,900 + 1*1,073,872,900 = 2,147,778,571 > INT_MAX (checked numerically), which is signed-overflow UB and in practice a negative index into `solid` (out-of-bounds read / crash) on the first _process rebuild. Far-fetched in isolation (the part needs ~3 GiB of fields plus a 3 GiB solid grid and an 8 GiB mask), so I would not fix it separately; it is evidence that the right fix for cpp-2 is a per-dimension cap (e.g. each dim <= 4096, far above the 48^3 heads) rather than only lowering the product cap, since that bounds every stride the mesher computes.
